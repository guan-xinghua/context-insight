## 1. 顶层角色（六个必须的角色）

一句话分工：**定义说标准 → 装配备料 → 评分器干活 → 聚合合账 → 基线提供参照 → 执行器串起来 → 呈现模块给人看**。

| # | 角色 | 干什么 |
|---|------|--------|
| 1 | 评分器 | 干活的（四个子类，见下） |
| 2 | 输入装配器 | 把 Session 装配成各评分器要的形状（轨迹摘要、工具调用表、用户消息表、测量值） |
| 3 | 聚合器 | **通用引擎，不认识具体维度**——只认"角色"和通用规则：否决维任一不过 → 总分不及格；加权维按权重合成（权重来自维度定义）；缺项/错误态 → 覆盖度折扣。子项怎么合成维度分，由各维度自带的聚合策略决定（见下） |
| 4 | 评分定义 | 不是执行者，是数据，装两样：**评分项 Schema**（结构定义：名称/类型/每档标准/角色/聚合策略/进不进总分，一源多用由它支撑）＋按 Schema 填的**实例**——内置实例（出厂预置，七维全部）和用户实例（D7）结构完全同一，差别只是数据来源 |
| 5 | 基线服务 | 基线库管理、同类任务分组判定，供基线对比评分器消费 |
| 6 | 执行器 | 编排：按维度调评分器 → 收错误态 → 记评审成本 → 交聚合 → 出评分卡 |
| 7 | 呈现模块 | **评分卡的所有读者**：评分 API（读卡、触发执行器）、Web/CLI/TUI 三端页面、报告导出。按维度结果列表**通用渲染**——得益于评分卡的列表结构，呈现层遍历列表按类型出组件，新维度自动有呈现，不用写专门页面 |

**评分器的四个子类**：

| 子类 | 产出什么 | 特点 |
|------|---------|------|
| 1.1 规则评分器 | 直接算出的值/判定（危险命令数、测试通过数、打断次数） | 同一 session 永远同分 |
| 1.2 LLM 评分器 | 评审分/分类（质量五维、消息九类） | 有抖动，要纪律约束 |
| 1.3 自定义评分器 | 用户定义的标准出的分（D7） | **= 1.2 + 用户定义的评分标准**，用户视角单列、实现复用 1.2，不另写一套 |
| 1.4 基线对比评分器 | 绝对量 → 和**已定义好的基线**比 → 位置分（token、工具时间、五类比率）。不是把一堆 session 拉出来实时排名——基线是现成的数据文件，比对即可 | **唯一读基线的：同一 session 的分会随基线更新（重新导入/重新生成）而变**——影响缓存与存储设计 |

## 4. 依赖关系与架构约束

### 4.1 依赖关系表

| 关系 | 方向 | 说明 |
|------|------|------|
| 工作流声明 → 装配器 | 单一来源 | 验收清单/红线/任务标签从一个接口取；写在 CLAUDE.md 还是工作流模板里，装配器不关心 |
| 评分定义 → LLM 评分器 | 单向供给 | 定义生成提示词和校验；内置还是 D7 用户写的，评分器无差别 |
| 装配器 → 所有评分器 | 单向供给 | 评分器要什么料在接口上声明 |
| 基线对比评分器 → 基线服务 | **唯一** | 其他评分器不许碰基线 |
| 所有评分器 → 聚合器 | 统一结果 | 聚合器不知道评分器类型——统一评分器接口的回报 |
| 维度定义（含聚合策略）→ 聚合器 | 策略随维度 | 子项怎么合成维度分由维度自带；聚合器只执行"角色"级通用规则 |
| 基线生成器 → 执行器 | 复用（远期） | 批量跑分复用同一套编排 |
| 评分卡 → 呈现模块 | 多端消费 | 呈现层只认评分卡结构（维度结果列表），不认识具体维度——列表结构的第二重回报 |

### 4.2 四条架构约束

1. **规则/LLM 评分器不认识基线**——对同一 session 永远同分（可缓存、可复算）；只有基线对比评分器的分随基线变
2. **错误态走正常通道**——任何评分器失败，错误记录照常交聚合器，按缺项打折，流程不断
3. **定义与执行分离**——评分定义是纯数据（可版本化、可被 D7 用户编辑），执行器是纯流程，互不依赖
4. **结果层与维度解耦（聚合器和评分卡都不认识具体维度）**——聚合器只认"角色"和通用规则；评分卡把维度结果存成统一结构的列表。检验标准：**新增一个维度，只加一份定义（含聚合策略），聚合器和评分卡结构零改动**（这次加 D7 就是这么检验的）

### 4.3 两个留口（先留接口不实现，见 design.md §9）

- **多次采样投票**：LLM 评审接口留"次数"参数，默认 1 次——需要更稳时调上去不用改结构
- **缺字段时 LLM 补抽**：装配器抽不到评分器声明的字段时，留"让 LLM 再补抽一次"的钩子


| ⑥ 执行器 | 离线 harness + 在线定时调度（checkpoint/采样/防饿死） | 在线调度器——已排进我们远期基线生成器 | —— |
| ① 装配器 | trace 解析 + 字段对齐 | 缺字段时 LLM 抽取兜底（已留口） | —— |
| ② 评分器 | Scorer 家族 | 供应商路由层（多 LLM 后端，现阶段单一通道够用）；第三方评分器桥接；多次采样投票（已留口） | **基线对比评分器**（它没有基线概念） |
| 评分定义 | JudgeField + prompt 模块 + make_judge | label_schemas（人工表单定义） | D7 独立成维（它是平铺 scorer 列表） |
| ③ 聚合器 | harness 聚合 + EnsembleScorer | 聚合函数库（多数投票、均值——聚合函数是可选数据，与我们的"策略随维度走"同路） | 三态组合、否决触发、覆盖度折扣、正确性压底——框架特有 |
| ⑤ 基线服务 | **无对应** | —— | 基线/同类分组/基线对比体系，我们独创 |
| ④ 评分卡 | Assessment 挂 TraceInfo | 挂载粒度可到单个 span；人工修正已有 | 否决标记 |
| 工作流声明 | expectations + guidelines | 期望答案作为一等数据 | 验收清单/红线/任务标签统一声明源 |
| ⑦ 呈现模块 | Traces 页的 assessments 展示、评测对比视图 | 评审结果可跳转到产出它的评审调用（评审自身可观测） | Web/CLI/TUI 三端同构消费同一评分卡 |

### 5.2 对照结论

1. **我们没有大块缺失**——它的每个角色我们都有对应物；在线调度已排远期，供应商路由现阶段不需要
2. **两个留口已补**（多次采样投票、缺字段补抽，见 §4.3）
3. **我们的差异化全在它没有的东西上**：维度框架、基线对比、否决机制、工作流声明统一源——正好各占一个独立角色，互不纠缠

4. 期间评分 API 返回 v2 结构，不做 v1 兼容层（无外部消费者，不必背过渡包袱）
